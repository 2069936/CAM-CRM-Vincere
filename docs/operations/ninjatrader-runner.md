# Controlled NinjaTrader build runner

The production AddOn must be compiled and parity-approved on a company-controlled
Windows machine with a licensed NinjaTrader 8 installation. This runner is a
build and verification host only. It must not be one of the client VPSs and must
not contain client accounts, algorithms, P&L, device credentials, or CRM secrets.

## Public-repository no-go

Do not register a self-hosted runner against the public
`pedro-cmyks/CAM-CRM-Vincere` repository. Workflow code executes directly on the
runner. Register it only at repository scope in the CAM-owned private mirror,
[`pedro-cmyks/CAM-CRM-Vincere-collector-build`](https://github.com/pedro-cmyks/CAM-CRM-Vincere-collector-build).
Repository-scoped registration is the access boundary for the current
personal-account repository. If the mirror later moves to a GitHub organization,
also place the runner in a dedicated group restricted to that repository.

The `ninjatrader-addon` job has two independent safety gates:

- it never runs for a `pull_request` event; and
- repository variable `COLLECTOR_PROPRIETARY_BUILD_ENABLED` must equal `true`.

Keep that variable absent or `false` until the private repository, runner access,
NinjaTrader references, and parity evidence all pass review. The signed release
job additionally uses the protected `collector-production` environment.

GitHub's current registration and service instructions are maintained in
[Adding self-hosted runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners),
and its isolation guidance is in the
[self-hosted runner reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).
Use the time-limited registration command generated by the private repository;
never copy its token into this repository, a ticket, or chat.

## Guided registration

Run these steps only on the dedicated CAM Windows build VM. They are not part of
the client collector installer and must never be run on a client VPS.

1. Clone or download the exact reviewed commit from the private mirror.
2. In the private repository, open **Settings > Actions > Runners > New
   self-hosted runner** and generate a short-lived repository registration token.
   Keep that page open; do not paste the token into a command, file, transcript,
   ticket, or chat.
3. Open an elevated PowerShell window in the checkout and inspect the mutation-free
   plan:

```powershell
& .\collector\scripts\install-private-ninjatrader-runner.ps1 `
  -RunnerName 'cam-nt-builder-01' `
  -CheckoutPath (Get-Location).Path `
  -PlanOnly | ConvertTo-Json -Depth 3
```

4. Run the same command without `-PlanOnly`. Paste the token only into the secure
   prompt:

```powershell
& .\collector\scripts\install-private-ninjatrader-runner.ps1 `
  -RunnerName 'cam-nt-builder-01' `
  -CheckoutPath (Get-Location).Path | ConvertTo-Json -Depth 3
```

The bootstrap downloads the pinned official Windows x64 runner, verifies its
SHA-256 before extraction, registers it as a Windows service with the required
`ninjatrader8` label, and targets only the private repository. The token is sent
to the runner through its temporary process input and is cleared afterward; it
is never placed in the command line. The script deliberately does not enable
`COLLECTOR_PROPRIETARY_BUILD_ENABLED`.

5. Confirm the runner appears online in the private repository. Keep the
   proprietary build variable `false` while the host references and real parity
   evidence are still being prepared.

## Required host state

1. Use a dedicated, patched Windows x64 VM controlled by CAM engineering.
2. Install the pinned GitHub Actions runner as a Windows service using the guided
   registration above. The current private repository owns the registration;
   use a restricted runner group as well if it moves to an organization.
3. Register the default `self-hosted`, `windows`, and `x64` labels plus the custom
   `ninjatrader8` label. The workflow requires `self-hosted`, `windows`, and
   `ninjatrader8`.
4. Install the licensed, approved NinjaTrader 8 version outside the runner
   checkout. Its `bin` directory must contain nonempty copies of:
   `NinjaTrader.Core.dll`, `NinjaTrader.Gui.dll`, and
   `NinjaTrader.NinjaScript.dll`.
5. Generate reviewed supported-API parity evidence with the repository probe.
   Store that JSON outside the checkout in a private directory readable only by
   Administrators and the runner service identity.
6. Set machine-level `NINJATRADER_HOME` and
   `NINJATRADER_PARITY_EVIDENCE` for the runner service, then restart the service
   so it receives the new environment. Do not store either artifact in Git.
7. Do not install UIAutomation references, the pixel/mouse prototype, production
   CRM credentials, signing material, or client exports on this host.

The parity evidence must represent the exact reviewed environment and cover a
same-minute four-section comparison, post-reset Realized/Gross behavior, two
strategy algorithms, and current-session executions. A placeholder report must
not be used to make the build green.

## Readiness check

From a fresh private checkout, run in PowerShell using the same identity as the
runner service:

```powershell
& .\collector\scripts\test-ninjatrader-runner-readiness.ps1 `
  -NinjaTraderHome $env:NINJATRADER_HOME `
  -ParityEvidencePath $env:NINJATRADER_PARITY_EVIDENCE `
  -CheckoutPath (Get-Location).Path | ConvertTo-Json -Depth 3
```

Success returns only `runner_ready` and named pass/fail checks. Errors are stable
path-free codes such as `runner_missing_ninjatrader_gui`,
`runner_ninjatrader_inside_checkout`, or
`runner_parity_evidence_inside_checkout`. Do not replace these with output that
prints private paths.

After the preflight passes:

1. Set private-repository variable
   `COLLECTOR_PROPRIETARY_BUILD_ENABLED=true`.
2. Trigger **Collector Windows** manually for the exact reviewed commit.
3. Confirm `ninjatrader-addon` compiles the .NET Framework 4.8 production AddOn,
   validates the complete parity report, and publishes the four-file runtime
   payload plus `addon-verification.json`.
4. Confirm the receipt SHA-256 matches the reviewed AddOn and parity evidence.
5. Remove or set the enable variable to `false` after the controlled build unless
   a release window is active.

The job staying queued is not evidence of compilation. A successful portable job
proves contracts, host-source syntax, agent, UI, installer authoring, and tests;
only a completed `ninjatrader-addon` job proves compilation against the real
NinjaTrader assemblies.

## Maintenance and incident response

- Keep runner application logs in protected centralized storage and retain them
  for the approved build-audit window.
- Patch Windows, NinjaTrader, .NET, and the Actions runner before enabling a new
  build window.
- Recreate the VM after any untrusted-code exposure or suspected credential
  access. Revoke the runner registration and signing credentials if applicable.
- Never return proprietary NinjaTrader assemblies as artifacts. Only the
  Vincere-owned DLL and its value-free verification receipt may leave the host.
- Remove the enable variable and take the runner offline when no controlled build
  is planned.
