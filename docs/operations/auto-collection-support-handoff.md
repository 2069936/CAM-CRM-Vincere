Status: **handoff template ready; ownership and production acceptance pending**.

This runbook assigns responsibilities without exposing personnel, client, or
credential details in the repository. Names, on-call schedules, access grants,
and approval records belong in the private operational system.

device token, signing certificate, or raw queue snapshot. Release/signing and
database access remain least-privilege engineering duties.

## Daily operating handoff

The daily owner must be able to:

1. Open Manager → Auto Collection and run the read-only audit after 17:00 ET.
2. Reconcile expected/received/incomplete/late/offline/update-required counts.
3. Assign every nonhealthy opaque reference to an owner and disposition.
4. Distinguish a normal duplicate retry from duplicate normalization.
5. Keep a day open for incomplete/failed data and preserve immutable history.
6. Use manual Accounts, Strategies, Orders, and Executions upload whenever the
   automatic path is not accepted for that device/day.

The status meanings and response targets are in
`docs/operations/auto-collection-status-codes.md`; recovery procedures are in
`docs/operations/auto-collection-runbook.md`.

## Supported actions and authorization

- Enrollment/rebind/revoke occurs only from the resolved client Profile.
- Open-day replay requires a Manager reason and exact confirmation.
- Closed-day replacement requires separate Manager authorization, reason,
  exact client/date confirmation, lineage, audit, and an operational flag.
- Diagnostics are generated by the agent UI and transferred through the
  approved private channel; staff never manually zip ProgramData.
- Repair/update uses only the pinned Profile download whose manifest hash and
  Authenticode signer match the approved release.
- Rollback retains unsent queue data and immutable CRM evidence.

## Incident handoff

Immediately stop the active wave for cross-client routing, secret exposure,
unsigned/tampered artifacts, duplicate normalization, missing acknowledged
data, systematic P&L mismatch, or possible data loss. The incident owner:

1. pauses new enrollment and removes the affected release download if needed;
2. revokes only resolved affected devices;
3. preserves queue, raw object, audit, version/hash, and redacted diagnostics;
4. restores manual collection and the previous approved package;
5. records impact using opaque references and aggregate counts; and
6. releases corrected bits under a new version/hash only after all gates pass.

## Competency sign-off

Each assigned team role must demonstrate its applicable items in staging or an
approved disposable VM:

- [ ] Install from Profile, verify returned client, restart NinjaTrader, and
      produce a green four-section test capture.
- [ ] Explain New York scheduling, grace, daily reset, and Realized/Gross
      fallback without editing captured values.
- [ ] Diagnose AddOn unavailable, offline queue, incomplete data, revoked token,
      late closed-day data, and update-required status.
- [ ] Generate and inspect a redacted diagnostics ZIP without snapshot or
      credential exposure.
- [ ] Replay an open day and execute the controlled closed-day replacement in
      staging with full audit evidence.
- [ ] Revoke/rebind one disposable device and prove the prior credential cannot
      upload.
- [ ] Repair, upgrade, roll back, and uninstall on the clean Windows image while
      retaining unsent data.
- [ ] Switch to the manual four-CSV workflow and complete the normal CRM review.

## Acceptance boundary

Manual upload remains enabled for the approved observation period. Removing it
is a separate change and cannot be inferred from fleet installation count.
Handoff is complete only after the production artifact, pilot, waves, daily
monitoring, incident exercises, and support competency checks have direct
evidence linked from the master completion audit.
